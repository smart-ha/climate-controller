# Climate Controller для Home Assistant

[![hacs_badge](https://img.shields.io/badge/HACS-Custom-orange.svg)](https://github.com/hacs/integration)
[![Validate](https://github.com/smart-ha/climate-controller/actions/workflows/validate.yml/badge.svg)](https://github.com/smart-ha/climate-controller/actions/workflows/validate.yml)

Кастомная интеграция, которая объединяет несколько нагревательных и охлаждающих
устройств под одной `climate`-сущностью с PID-регулированием, пресетами и
опциональным расписанием температуры по времени суток.

Одна виртуальная термостат-сущность управляет любым набором `climate.*`,
`switch` и `input_boolean` устройств, держит комнату у целевой температуры и
плавно, без резких перепадов, подводит кондиционер/обогреватель к нужному
режиму.

## Возможности

- **Одна `climate`-сущность на комнату.** HVAC-режимы `OFF` / `AUTO`, работа как
  обычный термостат в UI и во внешних интеграциях (Яндекс, Google, HomeKit —
  через `TURN_ON` / `TURN_OFF`).
- **Плавная регулировка без переохлаждения.** Целевая температура, которую
  интеграция выставляет на устройстве, привязана к **текущим показаниям датчика**
  и никогда не отклоняется от них больше чем на 4 °C — ни в охлаждении, ни в
  нагреве. Вместо «датчик 27 °C, кондиционер морозит на 16 °C» цель плавно
  сползает вместе с комнатой.
- **Пресеты.** `work`, `chill`, `sleep` с фиксированными температурами по
  умолчанию, плюс `none` — «без пресета». Ручная установка температуры
  автоматически сбрасывает активный пресет в `none`.
- **Расписание по времени суток.** Для каждого пресета — опциональные точки
  `время → температура` с линейной интерполяцией (циклической через полночь).
- **Недельное расписание присутствия.** Сетка 24×7 (час × день недели),
  которую интеграция **сама заполняет по датчику движения**: для каждого часа
  считается доля недель, в которые движение было. Превысила порог — час
  становится «человек ожидается». Поверх — ручные ячейки, которые всегда
  главнее обученных. Отдельно настраивается **предпрогрев**: за сколько минут
  до ожидаемого часа начинать греть, чтобы пол был уже тёплым. Для каждого из
  двух состояний задаётся своё действие — выключить, включить или выставить
  пресет (см. ниже).
- **Разные типы устройств.** `climate.*` (через PID-сдвиг `set_temperature`),
  `switch` / `input_boolean` (через ШИМ — time-proportional on/off). Устройство,
  заданное и на охлаждение, и на нагрев, работает в двунаправленном режиме.
- **Флаг `passive`.** Устройство можно только наблюдать, не управляя им
  (см. ниже).
- **Флаг `direct` — прямое управление.** Для техники, которая регулирует
  комнату сама (тёплый пол со своим термостатом): устройству просто
  передаётся та же уставка, что стоит на контроллере — без PID, без лимита
  отклонения и без парковки в idle-зоне.
- **Восстановление состояния** после перезапуска Home Assistant
  (HVAC-режим / пресет / целевая температура).

## Установка

### Через HACS (рекомендуется)

1. HACS → ⋮ (меню в правом верхнем углу) → **Custom repositories**.
2. Добавьте `https://github.com/smart-ha/climate-controller`, категория —
   **Integration**.
3. Найдите **Climate Controller** в списке и нажмите **Download**.
4. Перезапустите Home Assistant.
5. **Настройки → Устройства и службы → Добавить интеграцию → Climate Controller**.

### Вручную

1. Скопируйте папку `custom_components/climate_controller` в директорию
   `custom_components` вашего Home Assistant.
2. Перезапустите Home Assistant.
3. Добавьте интеграцию через **Настройки → Устройства и службы → Интеграции**.

## Настройка

После добавления интеграции откройте её **Настройки (Configure)** — там
меню-ориентированный OptionsFlow:

- **Devices & sensors** — датчики температуры (можно выбрать несколько) и
  способ их объединения, порог переключения cooling/heating, фиксированные
  температуры пресетов, списки нагревательных и охлаждающих устройств и по паре
  чекбоксов **Enable** / **Passive** на каждое.
- **Sleep / Work / Chill schedule** — точки расписания для каждого пресета
  (добавление по одной, массовое редактирование, удаление).
- **Save & exit** — применяет накопленные изменения и перезагружает интеграцию.

## Несколько датчиков температуры

На экране **Devices & sensors** можно выбрать не один датчик, а сколько угодно —
например, по одному на комнату, когда контроллер управляет котлом на весь дом.
Их показания сводятся в одно значение `current_temperature`, которое и получает
PID-контур. Способ выбирается там же:

| Метод | Что делает | Когда брать |
|---|---|---|
| **Average** (по умолчанию) | среднее по всем датчикам | дом в среднем; мягче всего по расходу топлива |
| **Minimum** | самый холодный датчик | греть, пока не прогреется самая холодная комната |
| **Maximum** | самый тёплый датчик | остановиться, как только прогрелась самая тёплая — защита от перегрева |
| **Median** | медиана | как среднее, но один сбойный датчик не уводит контур |

Недоступные датчики **пропускаются**, а не обнуляют результат: в доме с
батарейными датчиками одна севшая батарейка не должна останавливать котёл.
Контур замирает, только если непригодны *все* датчики.

Разложение видно прямо в атрибутах сущности — `temperature_readings` с
показанием каждого датчика, `temperature_sensors_unavailable` со списком
выпавших и `temperature_aggregation` с выбранным методом. Без этого на вопрос
«почему сейчас греет?» ответить нельзя.

Старые конфигурации мигрируют сами: единственный `temperature_sensor`
превращается в список из одного элемента с методом `Average`, который для одного
датчика равен самому показанию — поведение не меняется, пока не добавлен второй.

## Ограничение отклонения уставки (`max_delta`)

Контроллер никогда не просит у `climate.*` устройства температуру, отличающуюся
от **измеренной** больше чем на `max_delta` градусов. Это то, что делает
регулирование мягким: вместо того чтобы загонять кондиционер в минимум, когда в
комнате жарко, уставка устройства «скользит» вместе с комнатой.

Раньше предел был жёстко зашит в 4 °C для всех устройств. Теперь он задаётся
**для каждого термостата отдельно** на экране **Devices & sensors** — рядом с
чекбоксами **Enable** / **Passive** появляется поле с шагом 0.5 °C. По умолчанию
4 °C, то есть у существующих конфигураций ничего не меняется.

Зачем разные значения: 4 °C разумны для кондиционера, который реагирует за
минуты и работает в тех же градусах, что и воздух в комнате. Но у отопительного
котла уставка — это температура **теплоносителя**, а не воздуха: при 21 °C в
доме котлу нужно 50-60 °C в контуре, и с пределом в 4 °C он никогда их не
получит. Такому устройству ставьте широкий диапазон.

Поле есть только у `climate.*` устройств — у `switch` / `input_boolean` нет
уставки, они управляются широтно-импульсно.

Если одно и то же устройство добавлено и в нагрев, и в охлаждение (bidir), то из
двух заданных значений действует **меньшее** — иначе одна сторона молча
ослабляла бы предел, который другая намеренно ужесточила.

Порядок применения при вычислении уставки: PID-сдвиг → ограничение
`измеренная ± max_delta` → собственные `min_temp` / `max_temp` устройства →
округление к шагу устройства. Собственные пределы устройства всегда сильнее:
если кондиционер не умеет ниже 16 °C, он и не получит меньше.

## Устройство вернулось из `unavailable`

Пока устройство недоступно (завис Wi-Fi-модуль, пропало питание), контроллер
пропускает любые команды к нему. Вернувшись, устройство приходит в *своём*
последнем состоянии — например, котёл снова в `heat`, хотя зона давно в простое
или в `cooling`. Поэтому контроллер следит за своими устройствами и в момент
перехода `unavailable` / `unknown` → доступно сразу приводит устройство к нужному
состоянию:

| Состояние контроллера | Что происходит с вернувшимся устройством |
|---|---|
| `OFF` | выключается, как при переходе AUTO → OFF |
| зона простоя | паркуется: `switch` выключается, `climate.*` → `fan_only` / `off` |
| активная зона другой стороны (котёл при `cooling`) | паркуется так же |
| активная зона своей стороны | PID сбрасывается и регулирование применяется сразу, без ожидания тика |

Пассивные устройства не трогаются — их и так ведёт каждый тик.

## Флаг `passive` — устройства, которые не выключаются

Для каждого устройства в `cooling_devices` и `heating_devices` на экране
**Devices & sensors** доступен чекбокс **Passive** (по умолчанию выключен). Он
определяет, что происходит с устройством, когда контроллер уходит в `OFF`.

- **`passive = false` (обычный режим).** Устройство подчиняется зонной машине
  состояний. В `AUTO` контроллер ведёт его PID'ом, а у цели (idle-зона) —
  паркует. При переходе контроллера в `OFF` устройство **физически выключается**
  — `switch` / `input_boolean` через `turn_off`, `climate.*` через
  `set_hvac_mode=off`.
- **`passive = true` (всегда работает).** Устройство **никогда не выключается
  контроллером** и регулируется PID'ом к текущей целевой температуре на **каждом
  тике** — в `AUTO` (и в активной, и в idle-зоне), и когда контроллер в `OFF`.
  Перевод контроллера в `OFF` глушит обычные устройства, но passive-устройство
  продолжает вести комнату к цели. Основной кейс — **отопление, которое должно
  работать всегда**, поддерживая тепло даже когда комнатой не пользуются.

Регулировка идёт к той же `target_temperature`, что и у контроллера (с учётом
пресета / расписания / ручной установки). Снятие `passive` сразу возвращает
устройство под обычную зонную машину на следующем тике регулятора.

## Флаг `direct` — прямое управление

Тёплый пол со своим термостатом уже регулирует комнату. PID поверх него — это
два контура, гоняющиеся за одной температурой: наш сдвигает уставку, чужой на
неё реагирует, и оба считают, что виноват другой.

Галочка **`direct`** (в **Devices & sensors**, только у `climate.*`-устройств)
выключает нашу логику для конкретного устройства. Ему передаётся **ровно та
уставка, что стоит на карточке контроллера** — с учётом пресета, расписания и
ручной установки, но без:

- PID-сдвига,
- привязки к показаниям датчика (`max_delta` для такого устройства не
  применяется),
- зоны нечувствительности.

Единственное, что ещё правится, — собственные `min_temp` / `max_temp`
устройства и его шаг (`target_temp_step`).

Отсюда же следует остальное поведение:

- **Не паркуется в idle-зоне.** Обычное устройство, когда комната дошла до
  цели, уходит в `fan_only` / `off`. Для тёплого пола это означало бы, что мы
  выключаем ровно тот термостат, которому только что доверили комнату, — так
  что `direct`-устройства зонная машина не трогает.
- **Выключается вместе с контроллером.** Решение «работать или нет» остаётся
  нашим: переход контроллера в `OFF` отправляет устройству `set_hvac_mode=off`.
  Нужно, чтобы не выключалось вообще, — поставь рядом `passive`.
- **Уставка ставится точно.** Обычный путь пропускает вызов, если устройство
  уже в пределах `temp_threshold` от цели (это верный допуск для PID и неверный
  здесь). Для `direct` сравнение точное, так что на устройстве стоит то же
  число, что на карточке.

Комбинации:

| `direct` | `passive` | Поведение |
| --- | --- | --- |
| — | — | обычный режим: PID, лимит отклонения, парковка в idle |
| ✓ | — | своя уставка, не паркуется; выключается вместе с контроллером |
| ✓ | ✓ | своя уставка, не паркуется и не выключается никогда |
| — | ✓ | PID ведёт его всегда, в том числе когда контроллер в `OFF` |

## Недельное расписание присутствия (сетка 24×7)

Отопление пола не включается мгновенно: к моменту, когда человек пришёл, греть
уже поздно. Поэтому контроллер учится, **когда комнатой пользуются**, и
включается заранее.

Неделя разбита на 168 часовых слотов (час × день недели, понедельник первый).
Каждый слот наблюдается ровно раз в неделю, и его **коэффициент** — это доля
последних недель, в которые в этот час было движение. Движение в понедельник в
13:00 в 2 неделях из 4 даёт `0.5`. Слот, дотянувший до порога, становится
«человек ожидается».

| Цвет ячейки | Что значит |
| --- | --- |
| 🔵 синий | обучено по датчику: коэффициент ≥ порога |
| 🟠 рыжий | поставлено руками — «всегда ожидается» |
| ▫️ рыжая рамка | снято руками — «никогда», даже если обучение говорит обратное |
| ⚪ серый | движение было, но коэффициента не хватило |
| — пусто | движения в этот час не было ни разу |
| полупрозрачный | предпрогрев: слот ещё не начался, но греть уже пора |

**Ручное всегда главнее обученного.** Серый — это не «выключено», а
«посмотри сюда, когда выбираешь порог»: он показывает, что в этот час жизнь
есть, просто нерегулярная.

### Два состояния и действия

Состояний ровно два — **ожидается** и **не ожидается**. Для каждого в опциях
выбирается действие: ничего не делать, выключить контроллер, включить (`AUTO`)
или выставить пресет (`work` / `chill` / `sleep`). Действие применяется **один
раз, в момент перехода** — ручное вмешательство между переходами не трогается,
а на следующем переходе расписание снова берёт верх.

Предпрогрев — не третье состояние: это то же «ожидается», просто включённое на
`preheat_minutes` раньше. Живое движение тоже даёт «ожидается» немедленно, даже
если слот пустой: человек, пришедший в неурочное время, всё равно хочет тёплый
пол.

### Настройка

**Настройки → Устройства и службы → Climate Controller → Настроить →
Occupancy schedule**:

- **Motion sensors & preheat** — датчики движения (`binary_sensor` с
  `device_class` motion / occupancy / presence), время предпрогрева и сколько
  держать состояние «ожидается» после последнего срабатывания. **Датчики
  опциональны**: с ними сетка заполняется сама, без них она целиком твоя —
  расписание, нарисованное руками на карточке, работает и с пустым списком
  датчиков. Обучение стартует сразу, как только выбраны датчики; галочка
  включает только право расписания **переключать** контроллер — так можно
  сначала неделю посмотреть, как заполняется сетка, и лишь потом отдать ей
  комнату.
- **Learning window & threshold** — окно обучения в неделях (по умолчанию 4 —
  месяц), порог `0–1` (по умолчанию `0.5`) и сколько дней накопить, прежде чем
  обученные ячейки начнут что-то включать.
- **Actions per state** — действия для двух состояний.
- **Clear / reset the grid** — снять все ручные ячейки или забыть обученное.
  Применяется сразу, не по «Save & exit».

Обученная история и ручные ячейки хранятся **не в конфиге интеграции**, а в
`.storage/climate_controller.<entry_id>.occupancy` — их переписывает каждый клик
по карточке и каждая смена часа.

### Карточка

Сетка рисуется собственной Lovelace-карточкой — она лежит в репозитории в
`lovelace/` и деплоится скриптом в `www/climate-controller/`. HACS ставит этот
репозиторий как *интеграцию* и до `www/` не дотягивается, так что при установке
через HACS файл нужно скопировать в `config/www/climate-controller/` руками.

Один раз зарегистрировать ресурс: **Настройки → Панели → Ресурсы →
Добавить**, URL `/local/climate-controller/climate-controller-schedule-card.js`,
тип **Модуль JavaScript**. Затем в дашборд:

```yaml
type: custom:climate-controller-schedule-card
entity: climate.climate_controller
```

Клик по ячейке переключает её `обучено → снято руками → авто`, пустую —
`пусто → включено руками → авто`. Протягиванием выделяется прямоугольник — за
один вызов сервиса можно закрасить хоть все будние вечера.

**Сетка правится только здесь.** В OptionsFlow редактора сетки нет — там
только датчики, окно/порог, действия и очистка. Если карточку ставить не
хочется, те же ячейки задаются сервисом `climate_controller.set_occupancy_slot`
из **Developer tools → Actions**:

```yaml
action: climate_controller.set_occupancy_slot
target:
  entity_id: climate.climate_controller
data:
  day: [0, 1, 2, 3, 4]   # пн–пт
  hour: [18, 19, 20, 21] # 18:00–21:59
  mode: active
```

### Сервисы

| Сервис | Что делает |
| --- | --- |
| `climate_controller.set_occupancy_slot` | Задаёт ячейки: `day` (0 = понедельник) и `hour` — скаляр или список, применяются как прямоугольник; `mode` — `active` / `inactive` / `auto` |
| `climate_controller.clear_occupancy_overrides` | Снимает все ручные ячейки, обученное не трогает |
| `climate_controller.reset_occupancy_learning` | Забывает обученное, ручные ячейки сохраняет |

Сетка и её метаданные видны в атрибутах сущности: `occupancy_grid` (7×24 кодов
ячеек), `occupancy_scores` (коэффициенты в процентах, `-1` — ни разу не
наблюдался), `occupancy_state`, `occupancy_learning_days`.
